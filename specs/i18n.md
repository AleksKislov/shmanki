# Internationalization Specification

## Purpose

This document defines how language and localization work across the product.
It covers UI language, study-content language ownership, API expectations, and current scope limits.

---

## Goals

- Support multilingual UI for the web app and future mobile apps
- Keep study content language explicit and consistent
- Make language metadata predictable across database, backend, and frontend
- Avoid premature complexity such as per-card language overrides or language-specific answer grading rules

---

## Core Model

Two language concepts exist in the system:

- `user.preferredLanguage` — the user's chosen UI language
- `deck.languageCode` — the language of all study content inside that deck

Rules:

- `user.preferredLanguage` is the default language for newly created decks
- `deck.languageCode` is the source of truth for all nested content in the deck
- `info_objects` and `cards` inherit deck language and do not store language overrides in this version
- Review scheduling and FSRS are language-agnostic

---

## Language Code Format

All language identifiers use BCP 47 codes.

Examples:

- `en`
- `ru`
- `es`
- `de`
- `fr`
- `ja`
- `zh-CN`

Rules:

- Persist canonical codes only
- Validate codes at API boundaries
- Use the same code values across DB, backend DTOs, frontend types, and translation resources

---

## Data Ownership

### User

- Field: `preferred_language` in DB
- API field: `preferredLanguage`
- Meaning: UI locale and default language for new decks

### Deck

- Field: `language_code` in DB
- API field: `languageCode`
- Meaning: source of truth for titles, content, questions, distractors, and generated material inside the deck

### Info Objects and Cards

- No dedicated language field in this version
- Inherit language from parent deck
- If future requirements need mixed-language decks, add overrides intentionally in a later revision

---

## UI Localization

The frontend localizes all user-facing interface text based on `user.preferredLanguage`.

Requirements:

- All user-facing strings must come from translation resources
- Translation keys must be stable and semantic, e.g. `nav.decks`, `auth.login`, `deck.language`
- Fallback order is: current locale -> `en` -> translation key
- Layouts and components must tolerate longer translations and non-Latin scripts
- Localization applies to web now and should be reusable by future mobile clients

Out of scope for this version:

- RTL-specific layout adaptations
- locale-specific typography systems
- localized backend error messages

---

## Deck Language Behavior

When creating content:

- Registration may set `preferredLanguage`
- New deck forms default `languageCode` from the user's `preferredLanguage`
- Users may explicitly change a deck's `languageCode`
- All new info objects and cards created inside a deck are treated as content in that deck language

When editing content:

- Deck language remains the parent-level source of truth
- Changing deck language is allowed, but the product should treat it as a content-level decision, not just a UI preference
- Existing content is not auto-translated by changing `languageCode`

---

## Generation Rules

LLM generation must use the deck language.

Requirements:

- Prompt construction must include the deck `languageCode`
- Generated title, content, card fronts, correct answers, and distractors must match the deck language
- Backend validation must not assume English-only text
- Programming content may still use code-specific `content_type` values while surrounding explanatory text follows the deck language

---

## Review and Scheduling

Review mechanics are not localized in a language-specific way yet.

Current behavior:

- Token matching uses stored `correct_answers`
- FSRS rating derives from answer correctness and attempt metadata
- No stemming, inflection handling, grammar normalization, or synonym expansion yet

This keeps the scheduling system independent from language-specific grading rules.

---

## API Expectations

Recommended request/response behavior:

- Auth register request may include `preferredLanguage`
- Auth responses should include `user.preferredLanguage`
- Deck create/update requests should include `languageCode`
- Deck responses should include `languageCode`
- Review payloads do not need extra language fields because cards inherit deck language

---

## Frontend Expectations

- Store the authenticated user and current locale consistently
- Keep translation dictionaries under `frontend/src/lib/locales/`
- Use a shared i18n helper for translation lookup and fallback
- Avoid hardcoded labels in components, routes, forms, and empty states

---

## Backend Expectations

- Validate and normalize language codes centrally
- Default deck language from `users.preferred_language` when missing in create requests
- Persist language metadata on users and decks only in this version
- Keep internal business logic and generation flows language-aware, but not language-specialized

---

## Scope Limits

Not included in this version:

- Per-info-object language overrides
- Per-card language overrides
- Automatic translation of existing content
- Localized backend validation/error text
- Language-specific answer interpretation rules

These can be added later if product requirements justify the added complexity.
