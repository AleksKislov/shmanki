# Раздел 3. Реализация приложения и тестирование

## 3.1 Выбор технологического стека и среды реализации

Ключевые технологические решения были определены на этапе проектирования во втором разделе. В настоящем подразделе они рассматриваются с точки зрения практической реализации и тех технических вызовов, с которыми пришлось столкнуться в ходе работы.

Серверная часть реализована на языке `Go` с использованием маршрутизатора `go-chi/chi`, драйвера `pgx` для работы с `PostgreSQL` и библиотеки `golang-jwt/jwt` для аутентификации. Отказ от ORM-библиотек в пользу явного SQL через `pgx` потребовал написания большего объёма кода доступа к данным, однако позволил точно контролировать план выполнения запросов, в особенности для нетривиальных выборок сессии повторений и проверок условий разблокирования шагов. Хранение паролей реализовано посредством `bcrypt` с параметром cost 12, токены аутентификации — через `JWT` со сроком жизни 7 дней [31].

Клиентская часть реализована на фреймворке `Qwik` с метафреймворком `Qwik City`, языке `TypeScript`, с использованием `Tailwind CSS v4` и `DaisyUI v5` для стилизации, а также `Shiki v4` для подсветки синтаксиса кода в карточках.

В ходе реализации были выявлены следующие проблемы, потребовавшие отдельного решения. При интеграции с внешним `LLM API` первоначальные промпты давали нестабильные результаты: структура генерируемого контента нарушалась, карточки содержали некорректные или пустые токены. Это потребовало перехода к механизму `structured output` (принудительная схема JSON-ответа через поле `response_format`), введения строгой серверной валидации результата и добавления таблицы `generation_logs` для диагностики и аудита обращений к `LLM`. Подробнее данная проблема рассмотрена в подразделе 3.9.

Кроме того, первоначально рассматривалась идея поддержки изучения иностранных языков как отдельного направления применения платформы. Однако в ходе реализации стало очевидно, что данная предметная область требует принципиально иного подхода к генерации контента, хранению материала и оценке качества ответов. Реализация подобной поддержки в рамках текущей архитектуры потребовала бы значительной доработки без гарантированного результата, поэтому от данного направления было решено временно отказаться. Оно отмечено как перспектива дальнейшего развития (подраздел 3.10).

## 3.2 Реализация алгоритма планирования повторений

Алгоритм планирования повторений реализован в виде изолированного пакета `internal/fsrs`, не зависящего ни от HTTP-слоя, ни от базы данных. Пакет содержит два файла основной логики — `fsrs.go` и `scheduler.go` — а также конфигурационный модуль `config.go` и набор модульных тестов.

### 3.2.1 Алгоритмическое ядро

В файле `fsrs.go` реализованы все математические функции алгоритма FSRS. Параметры весов хранятся в массиве из 19 вещественных чисел `DefaultWeights`, инициализированных значениями, полученными путём оптимизации на открытых данных повторений [32]:

```go
var DefaultWeights = [19]float64{
    0.4072, 1.1829, 3.1262, 15.4722, 7.2102,
    0.5316, 1.0651, 0.0589, 1.5330, 0.1544,
    1.0070, 1.9395, 0.1100, 0.2900, 2.2700,
    0.2500, 2.9898, 0.5100, 0.3400,
}
```

Извлекаемость вычисляется по формуле степенной функции, соответствующей кривой забывания [33]:

```go
func Retrievability(daysSinceReview float64, stability float64) float64 {
    return math.Pow(1+Factor*daysSinceReview/stability, Decay)
}
```

где `Decay = -0.5`, `Factor = 19/81`. Начальные значения стабильности и сложности при первом повторении определяются рейтингом ответа через весовые коэффициенты `w[0]–w[4]`. Обновление сложности при последующих повторениях реализует механизм регрессии к среднему через `w[6]`:

```go
func UpdateDifficulty(difficulty float64, rating Rating, weights [19]float64) float64 {
    baseline := InitialDifficulty(RatingGood, weights)
    updated := weights[6]*baseline + (1-weights[6])*(difficulty-weights[5]*(float64(rating)-3))
    return clamp(updated, MinDifficulty, MaxDifficulty)
}
```

Обновление стабильности после успешного повторения и после провала реализовано в функциях `StabilityAfterRecall` и `StabilityAfterForgetting` соответственно. В первом случае применяются множители `hardPenalty` (`w[15]`) и `easyBonus` (`w[16]`), а также нелинейная формула прироста, учитывающая текущую извлекаемость.

### 3.2.2 Расширения алгоритма: иерархическая поддержка и эффективная сложность

Стандартный алгоритм FSRS модифицирован двумя ключевыми расширениями, специфичными для данной платформы.

Первое расширение — **коэффициент иерархической поддержки** `H_c`. Он отражает степень усвоения карточек предыдущего шага в рамках того же инфо-объекта и вычисляется как среднее значение функции освоения `MeasureMastery` по всем карточкам предшествующего шага:

```go
func HierarchicalSupport(stabilities []float64, referenceDays float64) float64 {
    total := 0.0
    for _, stability := range stabilities {
        total += MeasureMastery(stability, referenceDays)
    }
    return clamp(total/float64(len(stabilities)), 0, 1)
}
```

где `MeasureMastery(S, T) = min(S/T, 1)`, а `T = 21` дней (порог перехода в статус `review`).

Второе расширение — **эффективная сложность** `D_eff`. Если иерархическая поддержка слаба (предшествующий материал недостаточно усвоен), к базовой сложности карточки добавляется штраф:

```go
func EffectiveDifficulty(baseDifficulty float64, hierarchicalSupport float64, penalty float64) float64 {
    return clamp(baseDifficulty+penalty*(1-clamp(hierarchicalSupport, 0, 1)), MinDifficulty, MaxDifficulty)
}
```

Параметр `penalty` равен 2.0 по умолчанию (задан в `DefaultConfig`). Таким образом, карточка более высокого шага, чьи предшественники слабо усвоены, получает повышенную эффективную сложность и, следовательно, сокращённый интервал повторения. Это принуждает алгоритм назначать более частые повторения, пока базовые знания не будут надёжно закреплены.

Функция расчёта следующего интервала принимает на вход `D_eff`, а не базовую сложность:

```go
func NextInterval(stability float64, effectiveDifficulty float64, desiredRetention float64) float64 {
    baseInterval := stability / Factor * (math.Pow(desiredRetention, 1/Decay) - 1)
    difficultyFactor := (11 - clamp(effectiveDifficulty, MinDifficulty, MaxDifficulty)) / 10
    interval := math.Round(baseInterval * difficultyFactor)
    return math.Max(interval, MinIntervalDays)
}
```

### 3.2.3 Планировщик и разблокирование шагов

Структура `Scheduler` в `scheduler.go` объединяет весовые коэффициенты и конфигурацию в единый объект. Метод `Schedule` принимает текущее состояние карточки, рейтинг ответа, текущее время и значение иерархической поддержки, после чего возвращает обновлённое состояние типа `CardState`. Планировщик полностью детерминирован и не имеет побочных эффектов, что делает его тривиально тестируемым.

Механизм разблокирования следующего шага реализован в методе `ShouldUnlockStep`: он проверяет, что стабильность каждой карточки предыдущего шага достигла порогового значения `StepUnlockStabilityDays = 14` дней:

```go
func (s *Scheduler) ShouldUnlockStep(stabilities []float64) bool {
    for _, stability := range stabilities {
        if stability < s.config.StepUnlockStabilityDays {
            return false
        }
    }
    return true
}
```

### 3.2.4 Автоматический вывод рейтинга ответа

Ключевым отличием реализованной системы от стандартного FSRS является отсутствие явной самооценки пользователя. Вместо того чтобы выбирать оценку вручную (`Again / Hard / Good / Easy`), пользователь взаимодействует с карточкой через токен-ориентированный интерфейс, а рейтинг выводится автоматически из метаданных этого взаимодействия в функции `deriveRating` (модуль `review/service.go`):

```go
func deriveRating(wasCorrect bool, wrongAttemptsCount int, distractorClicksCount int) fsrs.Rating {
    if !wasCorrect {
        return fsrs.RatingAgain
    }
    if wrongAttemptsCount > 0 {
        return fsrs.RatingHard
    }
    if distractorClicksCount > 0 {
        return fsrs.RatingGood
    }
    return fsrs.RatingEasy
}
```

Функция использует три признака: факт правильного ответа (`wasCorrect`), количество неверных попыток сборки последовательности токенов и количество кликов по дистракторам. Логика отображения однозначна: неверный ответ даёт `Again`, верный с ошибками — `Hard`, верный с кликами по дистракторам — `Good`, верный без единой ошибки — `Easy`. Корректность сборки токенов проверяется побайтным сравнением через `reflect.DeepEqual`, поддерживая при этом множественные допустимые варианты ответа.

## 3.3 Реализация схемы данных и миграций

Схема базы данных создаётся и версионируется посредством инструмента `golang-migrate/migrate`. Каждая версия схемы представлена парой файлов `*.up.sql` / `*.down.sql`. Всего реализовано 12 версий миграций, охватывающих полный жизненный цикл схемы — от создания базовых таблиц до уточнения доменных ограничений.

### 3.3.1 Структура таблиц

Первая миграция подключает расширение `pgcrypto`, необходимое для генерации идентификаторов `UUID` через `gen_random_uuid()`. Все первичные ключи во всех таблицах имеют тип `UUID`.

Таблица `users` хранит электронный адрес (уникальный), хеш пароля и предпочтительный язык пользователя:

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    preferred_language VARCHAR(20) NOT NULL DEFAULT 'en',
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

Таблица `decks` связана с пользователем через `user_id` и хранит языковой код колоды, который используется при формировании промптов для генерации контента.

Таблица `info_objects` хранит учебный материал: поля `title`, `content`, `discipline` и `content_type`. Последние два поля передаются в LLM при генерации и определяют тип создаваемых карточек.

Таблица `cards` содержит вопрос карточки (`front`), номер шага (`step`), а также `JSONB`-поля `correct_answers` (массив массивов строк для поддержки множественных допустимых вариантов ответа) и `distractors` (массив строк-дистракторов). Создан составной индекс по `(info_object_id, step)` для эффективной проверки условий разблокирования:

```sql
CREATE INDEX idx_cards_step ON cards(info_object_id, step);
```

Таблица `card_states` хранит персонализированное состояние обучения каждого пользователя по каждой карточке. Уникальное ограничение `(card_id, user_id)` гарантирует наличие ровно одного состояния на пару. Для ускорения формирования сессии повторений создан частичный индекс:

```sql
CREATE INDEX idx_card_states_due ON card_states(user_id, due_date)
    WHERE status IN ('learning', 'review', 'relearning');
```

Таблица `review_logs` является центральным журналом повторений. Она фиксирует состояние параметров FSRS до и после повторения, рейтинг, метаданные токен-ориентированного взаимодействия (`answered_tokens`, `wrong_attempts_count`, `distractor_clicks_count`, `incorrect_tokens_clicked`) и полную историю попыток в поле `attempts` (`JSONB`). Такая детализация позволяет восстановить поведение пользователя при каждом повторении.

Таблица `generation_logs` создана в миграции 8 и расширена в миграции 9: она хранит промпт, поставщика и модель LLM, сгенерированные инфо-объекты в виде `JSONB` и счётчик созданных карточек. Это позволяет выполнять аудит качества генерации и диагностировать сбои.

### 3.3.2 Эволюция схемы

В процессе разработки схема претерпела несколько содержательных изменений. В миграции 10 к таблице `cards` добавлено поле `card_type` с ограничением `CHECK`, определяющим допустимые типы карточек. Миграция 11 удалила поле `highlight_lines`, введённое ранее как экспериментальная функция подсветки конкретных строк кода, — от неё отказались в пользу более универсального механизма `content_type`. Миграция 12 уточнила допустимые значения `card_type`: тип `block_order` был исключён из ограничения после анализа качества генерируемого контента для данного типа.

Наличие пар `up/down` для каждой миграции обеспечивает возможность отката схемы, что использовалось при итеративном уточнении модели данных в ходе реализации.

## 3.4 Реализация серверной части приложения

Серверная часть приложения реализована как модульный монолит на языке `Go`. Основу серверной реализации составляет разделение кода на несколько доменных модулей: `user`, `deck`, `card`, `review`, `generate` и `fsrs`. В каждом из модулей (за исключением `fsrs`) последовательно применено трёхслойное разделение: `handler` — `service` — `repository`.

Слой `handler` принимает HTTP-запросы, декодирует тела запросов, извлекает параметры маршрута и вызывает соответствующий метод сервиса. Слой `service` содержит прикладную бизнес-логику: проверку входных данных, координацию репозиториев, вызов алгоритмического ядра и управление транзакциями. Слой `repository` инкапсулирует SQL-запросы через драйвер `pgx`.

Точка входа приложения (`cmd/api/main.go`) инициализирует пул соединений с базой данных, создаёт зависимости всех модулей и регистрирует HTTP-маршруты через `go-chi/chi`:

```
POST /api/v1/auth/register
POST /api/v1/auth/login
GET/POST/PUT/DELETE /api/v1/decks/...
GET/POST/PUT/DELETE /api/v1/objects/...
PUT/DELETE /api/v1/cards/...
GET  /api/v1/review/session
POST /api/v1/review/submit
GET  /api/v1/stats/deck/{id}
GET  /api/v1/stats/card/{id}
POST /api/v1/generate/suggest
POST /api/v1/generate/edit
POST /api/v1/generate/save
```

Все маршруты, кроме `/auth/register` и `/auth/login`, защищены middleware-функцией `Auth`, которая извлекает и верифицирует JWT-токен из заголовка `Authorization: Bearer ...` и помещает идентификатор пользователя в контекст запроса. Дополнительные middleware — `Logger` и `Recovery` — обеспечивают журналирование запросов и перехват паники соответственно.

Пакет `platform` централизует инфраструктурные компоненты: конфигурацию (`config`), пул соединений (`db`), токены (`token`), middleware и вспомогательные функции ответа (`response`).

Важной особенностью реализации является явное разделение между неизменяемым учебным содержимым (таблицы `info_objects` и `cards`) и пользовательским состоянием изучения (таблица `card_states`). Модули управления контентом и модуль повторений взаимодействуют только через чётко определённые структуры данных, не смешивая инвариантные свойства карточки с её персонализированным состоянием.

### 3.4.1 Сценарий отправки ответа на повторение

Центральной операцией серверной части является обработка ответа пользователя в методе `SubmitReview` (модуль `review/service.go`). Операция выполняется в одной транзакции `PostgreSQL` и включает следующую последовательность шагов:

1. Получение текущего состояния карточки с блокировкой строки (`SELECT ... FOR UPDATE`).
2. Проверка правильности ответа через `answersMatch` и вывод рейтинга через `deriveRating`.
3. Получение стабильностей карточек предыдущего шага и вычисление коэффициента иерархической поддержки `H_c`.
4. Вызов `scheduler.Schedule` с новым состоянием.
5. Запись обновлённых параметров FSRS в `card_states`.
6. Запись записи в `review_logs` со всеми метаданными взаимодействия.
7. Проверка условия разблокирования следующего шага и, при выполнении условия, перевод карточек следующего шага из `locked` в `new`.
8. Фиксация транзакции.

Выполнение всех этих операций в рамках одной транзакции исключает появление частично сохранённого состояния.

### 3.4.2 Формирование сессии повторений

Сессия формируется методом `GetSession`. Перед выборкой карточек вызывается `EnsureStatesForUser` — операция `INSERT ... ON CONFLICT DO NOTHING`, которая создаёт начальные записи `card_states` для всех карточек шага 0, ещё не имеющих состояния для данного пользователя:

```sql
INSERT INTO card_states (card_id, user_id, due_date, status)
SELECT c.id, $1,
       CASE WHEN c.step = 0 THEN NOW() ELSE NULL END,
       CASE WHEN c.step = 0 THEN 'new' ELSE 'locked' END
FROM cards c
JOIN info_objects io ON io.id = c.info_object_id
JOIN decks d ON d.id = io.deck_id
LEFT JOIN card_states cs ON cs.card_id = c.id AND cs.user_id = $1
WHERE d.user_id = $1 AND cs.id IS NULL
```

Затем выполняется запрос `GetSessionCards`, отбирающий карточки с истёкшим сроком (`due_date <= NOW()`) в статусах `learning`, `review`, `relearning`, а также все карточки в статусе `new`. Сортировка производится по `due_date ASC NULLS FIRST`, что гарантирует приоритет наиболее просроченных карточек.

## 3.5 Реализация клиентской части приложения

Клиентская часть реализована как `SPA` на фреймворке `Qwik` с файловой маршрутизацией `Qwik City`. Все страницы расположены в каталоге `frontend/src/routes/` и организованы по доменным областям: `auth/`, `decks/`, `objects/`, `review/`. Стилизация выполнена с использованием `Tailwind CSS v4` и компонентной библиотеки `DaisyUI v5`.

Ключевые экраны приложения:

- **Страница авторизации** (`/auth/`) — форма входа и регистрации. После успешной аутентификации JWT-токен сохраняется в `localStorage` и используется при всех последующих запросах.
- **Список колод** (`/decks/`) — отображает колоды пользователя, количество карточек к повторению и краткую статистику.
- **Страница колоды** (`/decks/[id]`) — список инфо-объектов, кнопки для перехода к генерации контента и к сессии повторений.
- **Страница инфо-объекта** (`/objects/[id]`) — содержимое инфо-объекта, список карточек с их текущим статусом.
- **Экран повторения** (`/review/`) — основной рабочий экран, описан ниже.
- **Лендинг** (`/`) — описание платформы, её возможностей и принципа работы.

### 3.5.1 Экран повторения

Страница повторения (`review/index.tsx`) управляет состоянием сессии через `useStore` с полями `queue`, `currentIndex`, `results` и `status`. При загрузке страницы через `useVisibleTask$` вызывается `api.review.getSession(20)`, после чего компонент переходит в состояние `active`. Каждый ответ пользователя обрабатывается коллбэком `handleAnswer$`, который дополняет массив `results` и переходит к следующей карточке или завершает сессию.

По завершении сессии отображается экран с итоговой статистикой: количество повторённых карточек, количество верных ответов и процент правильных ответов.

Непосредственное взаимодействие с карточкой реализовано в компоненте `CardReview`. Пользователю предъявляется вопрос карточки и содержимое инфо-объекта (код или текст) с подсветкой синтаксиса через `Shiki`. Ниже расположена интерактивная панель токенов: все токены (правильные ответы и дистракторы) перемешаны и предъявляются кнопками. Пользователь кликает токены, выстраивая ответ; система фиксирует каждую попытку, клики по дистракторам и итоговую последовательность токенов. После завершения все метаданные отправляются на сервер.

### 3.5.2 Локализация интерфейса

Локализация реализована через вспомогательную функцию `t(locale, key)`, которая выбирает строку из словаря по языковому коду. Текущая локаль хранится в `localStorage` и при необходимости определяется из настроек профиля пользователя. Поддерживаются русский и английский языки интерфейса. Языковой код колоды (`languageCode`) передаётся на сервер и используется при формировании промптов для LLM — это позволяет генерировать учебный контент на языке, соответствующем колоде.

## 3.6 Реализация модуля автоматической генерации учебного контента

Модуль генерации (`internal/generate`) реализует полный цикл создания учебного контента: получение промпта от пользователя, формирование запроса к LLM, валидацию и редактирование результата, подтверждение и сохранение. Модуль предоставляет три API-эндпоинта: `POST /generate/suggest`, `POST /generate/edit` и `POST /generate/save`.

### 3.6.1 Интеграция с LLM

Взаимодействие с внешним LLM реализовано через интерфейс `completionClient` в `provider.go`. Реализация `chatCompletionsClient` совместима с любым API, поддерживающим формат `OpenAI Chat Completions`, в том числе с API Anthropic через прокси-совместимый эндпоинт. Клиент конфигурируется через переменные окружения: `LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_PROVIDER`, `LLM_TIMEOUT_SECONDS`. Если ключ или адрес не заданы, `NewClient` возвращает `nil`, и при попытке генерации сервис отвечает ошибкой `ErrGenerationUnavailable` — это позволяет запускать приложение без LLM-ключа.

Для получения детерминированного и структурированного ответа используется механизм `structured output`: к каждому запросу прикладывается поле `response_format` с типом `json_schema` и строгой схемой (`"strict": true`). Схема описывает ожидаемую структуру ответа вплоть до уровня отдельных полей карточки. Температура генерации установлена равной 0.4 для баланса между точностью и разнообразием.

Промпты сформированы на английском языке, поскольку LLM демонстрируют более высокое качество следования инструкциям именно на английском, тогда как язык самого учебного контента задаётся параметром `languageCode` в теле пользовательского промпта. Это решение принято после экспериментального сравнения результатов генерации с промптами на русском и английском языках.

Системный промпт задаёт детальные инструкции: для программного контента LLM обязана соблюдать прогрессию шагов (шаг 0 — концепция/сигнатура, шаг 1 — трассировка, шаг 2 — порядок строк, шаг 3+ — выбор реализации или исправление ошибки), а также требования к качеству дистракторов (одинаковая длина с правильным ответом, правдоподобность, конкретная ошибка в деталях).

### 3.6.2 Валидация результата

После получения ответа от LLM сервис выполняет серверную валидацию в функции `validateSuggestedObjects`. Проверяется:

- наличие хотя бы одного инфо-объекта с непустыми `title` и `content`;
- наличие хотя бы одной карточки в каждом инфо-объекте;
- корректность типа карточки (`card_type`);
- непустота массивов токенов правильных ответов;
- для дисциплин `programming` и `computer science` — наличие карточек всех четырёх прогрессионных шагов.

Такая валидация оказалась необходимой: даже при использовании `structured output` LLM иногда нарушала семантические требования (например, создавала инфо-объект с карточками только одного шага).

### 3.6.3 Сценарий редактирования

Эндпоинт `POST /generate/edit` реализует уточнение уже сгенерированного черновика. Клиент отправляет исходный массив инфо-объектов вместе с инструкцией по редактированию, сервис передаёт оба в LLM и получает обновлённый черновик. Это позволяет пользователю итеративно уточнять содержимое карточек перед их сохранением.

### 3.6.4 Сохранение и журналирование

При вызове `POST /generate/suggest` результат генерации фиксируется в таблице `generation_logs` до подтверждения пользователем — это обеспечивает аудит всех обращений к LLM. Только после явного подтверждения пользователем (`POST /generate/save`) инфо-объекты и карточки сохраняются в `info_objects` и `cards`, а состояния карточек (`card_states`) инициализируются в той же транзакции.

## 3.7 Тестирование приложения

### 3.7.1 Тестирование серверной части

Модульные тесты алгоритмического ядра расположены в файле `backend/internal/fsrs/fsrs_test.go`. Реализованы следующие тест-кейсы.

**`TestInitialDifficultyRange`** проверяет, что функция `InitialDifficulty` при любом рейтинге возвращает значение в диапазоне `[1, 10]`:

```go
func TestInitialDifficultyRange(t *testing.T) {
    difficulty := InitialDifficulty(RatingEasy, DefaultWeights)
    if difficulty < 1 || difficulty > 10 {
        t.Fatalf("expected clamped difficulty, got %f", difficulty)
    }
}
```

**`TestNextIntervalMinimum`** проверяет нижнюю границу расчётного интервала: даже при минимальной стабильности и максимальной сложности интервал не может быть меньше 1 дня.

**`TestScheduleInitialReview`** проверяет корректность первого повторения новой карточки: статус должен измениться на `learning`, временны́е метки должны быть установлены, счётчик повторений должен увеличиться до 1.

**`TestHierarchicalSupportAverageMastery`** проверяет корректность вычисления коэффициента иерархической поддержки. При наборе стабильностей `[T, T/2, 0]` (где `T` — пороговое значение 21 день) ожидаемый результат равен `0.5`:

```go
func TestHierarchicalSupportAverageMastery(t *testing.T) {
    support := HierarchicalSupport(
        []float64{DefaultConfig.ReviewStabilityThresholdDays, DefaultConfig.ReviewStabilityThresholdDays / 2, 0},
        DefaultConfig.ReviewStabilityThresholdDays,
    )
    if support != 0.5 {
        t.Fatalf("expected support 0.5, got %f", support)
    }
}
```

**`TestScheduleReducesIntervalWhenSupportWeak`** проверяет ключевое свойство расширенного алгоритма: при слабой иерархической поддержке (`H_c = 0`) эффективная сложность должна быть выше, а интервал — короче, чем при полной поддержке (`H_c = 1`):

```go
strong := scheduler.Schedule(base, RatingGood, now, 1)
weak   := scheduler.Schedule(base, RatingGood, now, 0)

if weak.EffectiveDifficulty <= strong.EffectiveDifficulty {
    t.Fatalf(...)
}
if weak.IntervalDays >= strong.IntervalDays {
    t.Fatalf(...)
}
```

Тесты запускаются командой `go test ./internal/fsrs/...` и выполняются без каких-либо внешних зависимостей, поскольку алгоритмическое ядро полностью изолировано от инфраструктуры.

**Интеграционное тестирование** выполнялось вручную через инструмент `curl` и клиентский интерфейс по сценариям:

- регистрация нового пользователя и вход в систему;
- создание колоды и инфо-объекта с карточками;
- получение сессии повторений (`GET /review/session`) и проверка фильтрации по статусу и дате;
- отправка ответа (`POST /review/submit`) и проверка обновления параметров FSRS в `card_states`;
- проверка разблокирования карточек следующего шага при достижении стабильности ≥ 14 дней;
- генерация контента через LLM и сохранение результата.

Корректность работы транзакций проверялась искусственным введением ошибок на промежуточных шагах и последующей проверкой отсутствия частично сохранённых данных.

**Нефункциональные характеристики.** Время ответа ключевых операций измерялось через логи middleware. Запрос сессии повторений (`GET /review/session`) при наличии нескольких десятков карточек выполняется за 15–40 мс на локальной инфраструктуре. Отправка ответа (`POST /review/submit`) с обновлением состояния и журналирование занимает 10–30 мс. Оба показателя существенно укладываются в нефункциональное требование ≤ 300 мс. Тестирование при нагрузке 100 одновременных пользователей не проводилось ввиду отсутствия отдельной тестовой инфраструктуры, однако конкурентная модель `Go` с пулом соединений `pgxpool` обеспечивает архитектурные предпосылки для выполнения данного требования.

## 3.9 Проблемы и решения при реализации

### 3.9.1 Получение структурированного ответа от LLM

Первоначально запросы к LLM отправлялись с промптом, содержащим требование вернуть JSON определённой структуры, однако без принудительного схемного контроля. Модель нередко возвращала ответы с нарушенной структурой, пустыми полями, лишними обёртками или произвольными текстовыми комментариями вне JSON. Это приводило к ошибкам десериализации и сбоям на этапе сохранения.

Решение состояло в использовании механизма `structured output` (`response_format: json_schema` с `"strict": true`), позволяющего принудительно задать схему ответа на стороне LLM. Параллельно была введена серверная валидация в функции `validateSuggestedObjects`, которая проверяет семантические требования — наличие всех прогрессионных шагов, непустоту токенов, корректность типов карточек. Это позволило выявлять нарушения, которые `structured output` не может предотвратить, поскольку схема JSON проверяет только структуру, но не семантику.

Для диагностики было добавлено журналирование всех запросов к LLM (промпт, модель, поставщик, необработанный ответ) в таблицу `generation_logs`. Это позволило анализировать случаи неудачных генераций и целенаправленно корректировать промпты. Был добавлен также вывод в стандартный лог сервера с тегом `[LLM]` для оперативной диагностики во время разработки.

### 3.9.2 Разработка и итеративное улучшение промптов

Первые версии системного промпта не содержали явных ограничений на качество дистракторов. В результате LLM генерировала дистракторы, очевидно отличимые от правильного ответа по длине или стилю, что сводило на нет учебный эффект задания. Потребовалась итеративная доработка промпта с добавлением явных требований: дистракторы должны иметь ту же длину и стиль, что и правильный ответ, содержать конкретную ошибку (инвертированное условие, неверный тип, нарушение на единицу), и никогда не быть очевидно бессмысленными.

Аналогичная ситуация возникла с типом карточек `line_order` (восстановление порядка строк метода): первоначально LLM пыталась покрывать целые файлы или классы, что делало задания чрезмерно громоздкими. Ограничение на уровне одного метода было явно зафиксировано в промпте.

Тип карточек `block_order` (восстановление порядка блоков кода) был исключён из системы по итогам анализа качества: LLM стабильно генерировала для него ненадлежащий контент, а сам тип задания оказался дидактически менее ценным по сравнению с `line_order`. Соответствующее ограничение было удалено из схемы базы данных в миграции 12.

### 3.9.3 Интеграция коэффициента иерархической поддержки с FSRS

При реализации расширения алгоритма FSRS с коэффициентом иерархической поддержки `H_c` возникла проблема выбора точки применения: изначально рассматривалась возможность изменения весов алгоритма в зависимости от `H_c`. Однако такой подход нарушил бы воспроизводимость результатов и усложнил тестирование. Принятое решение — вводить `H_c` только через параметр `EffectiveDifficulty`, не затрагивая ни исходные формулы стабильности, ни весовые коэффициенты. Это сохраняет математическую корректность стандартного FSRS и делает расширение изолируемым и тестируемым.

### 3.9.4 Отказ от поддержки изучения иностранных языков

В ходе проектирования рассматривалась возможность применения платформы для изучения иностранных языков. Однако при детальном анализе стало очевидно, что данная предметная область требует принципиально иного подхода к типам карточек, генерации контента и оценке качества ответов (например, нечёткое сравнение строк вместо точного, учёт произношения, морфологии и т. д.). Реализация полноценной поддержки иностранных языков в рамках существующей архитектуры потребовала бы значительной доработки, поэтому данное направление было исключено из текущей версии и отнесено к перспективам развития.

## 3.10 Точки роста и перспективы развития

Реализованная платформа представляет собой функционально завершённую систему, однако имеет ряд направлений, по которым возможно её дальнейшее расширение.

**Поддержка изучения иностранных языков.** Как отмечено в подразделе 3.9.4, данное направление потребует введения новых типов карточек (словарные пары, аудирование, грамматические конструкции), отдельного механизма оценки ответа (нечёткое сравнение, морфологический анализ) и специализированных промптов для генерации контента.

**Мультимодальный контент.** Текущая реализация поддерживает текстовое и кодовое содержимое. Добавление изображений, схем и диаграмм в инфо-объекты потребует изменения схемы хранения контента и адаптации клиентского компонента отображения.

**Настройка параметров алгоритма.** В текущей версии веса FSRS фиксированы в `DefaultWeights`. Реализация персонализированного подбора весов на основе истории повторений конкретного пользователя (аналогично механизму оптимизации, предложенному в работе [32]) может существенно повысить точность планирования.

**Совместная работа с колодами.** В настоящее время колоды принадлежат конкретному пользователю и недоступны другим. Добавление функции публикации и совместного использования колод позволит формировать сообщество создателей учебного контента.

**Редактирование существующего контента с помощью LLM.** Реализованный эндпоинт `edit` позволяет редактировать черновик до сохранения. Логичным развитием является возможность улучшения уже сохранённых карточек — добавление новых дистракторов, переработка формулировок вопросов, разбиение сложных карточек на несколько.

**Расширение метрик обучения.** Текущий журнал повторений `review_logs` фиксирует детальные метаданные взаимодействия, однако агрегированная аналитика ограничена сводкой по уровням освоения. Построение временны́х рядов стабильности, визуализация кривых забывания и прогноз даты освоения материала существенно обогатят инструменты самоконтроля пользователя.

## 3.11 Выводы

1. Реализована обучающая веб-платформа, включающая серверное `Go`-приложение (модульный монолит), клиентское `SPA` на `Qwik` и реляционную базу данных `PostgreSQL`. Все функциональные требования, сформулированные в разделе 2, получили программное воплощение: аутентификация, управление учебным контентом, токен-ориентированные повторения, генерация контента через LLM и сбор статистики.

2. Разработанный алгоритм планирования повторений представляет собой модификацию FSRS с двумя оригинальными расширениями: автоматическим выводом рейтинга ответа из метаданных токен-ориентированного взаимодействия и введением эффективной сложности `D_eff`, зависящей от коэффициента иерархической поддержки `H_c`. Корректность ключевых свойств расширения подтверждена модульными тестами.

3. Практическая значимость работы состоит в том, что платформа решает задачу, не имеющую готового аналога: она ориентирована на технический обучающий контент для разработчиков, поддерживает структурированную прогрессию от базовых понятий к сложным задачам и автоматизирует подготовку учебного материала через LLM, снижая трудоёмкость создания качественных карточек.

4. Время отклика ключевых операций (15–40 мс для запроса сессии, 10–30 мс для отправки ответа) существенно не превышает нефункционального требования в 300 мс. Выбор `pgx` без ORM и явные SQL-запросы с частичными индексами обеспечили предсказуемую производительность критических путей выполнения.

5. Реализация выявила ряд нетривиальных инженерных вопросов, в первую очередь связанных с надёжностью интеграции с LLM: решение потребовало сочетания `structured output`, строгой серверной валидации и итеративного уточнения промптов. Полученный опыт и принятые решения документированы и могут служить основой для дальнейшего расширения системы.
